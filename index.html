AI 代理架構選型研究室

從固定流程、單一代理到多代理協作，學會選擇合適架構，並用實作檢查效果。

✦01｜先問問題，再選 Agent

學習重點

最簡單可行架構

不要因為可以做 Multi-Agent，就一定使用 Multi-Agent。先建立基準線，再以瓶頸證明複雜度的必要。

架構能力

系統視角

分辨控制流程、資料流程、工具、模型、記憶、權限、人工核准與可觀測性。

實驗精神

有證據的選型

比較正確率、完成時間、成本、失敗恢復與維護負擔，而非比較 Agent 數量。

開場討論

「兩小時做出一個能查詢庫存的 Agent，代表它有企業價值嗎？」請先寫下你會要求的三項證據。

建議答案：

  1. 準確性：用相同的庫存問題比較 Agent 與現有系統，確認數量、庫位及更新時間是否正確，並測試查不到資料時會不會亂答。
  2. 實際效益：比較人工或原有查詢方式與 Agent 的處理時間、成功率及使用成本，證明它真的節省工作或改善品質。
  3. 穩定與安全：連續測試異常、權限及資料更新情境，確認不會洩漏不該看的庫存資料，且出錯時可追蹤與處理。

討論結論：兩小時做出來，證明開發速度快；只有通過上述驗證，才有理由主張具備企業價值。

◈02｜MCP：讓代理使用外部工具

MCP 是讓 AI 應用與外部工具、資料來源溝通的共同規格。先分清楚「誰發出請求」與「誰提供工具」，再學習如何安全串接。

一張圖看懂：主機、客戶端、伺服器

使用者→AI 應用（主機）
內含 MCP 客戶端⇄MCP 伺服器⇄資料庫／外部服務

MCP Client（客戶端）

負責連線、取得可用工具清單、提出工具呼叫，並接收結果。它通常在 AI 應用或代理執行環境中。

例：n8n 的 MCP Client Tool，讓代理能呼叫外部 MCP 伺服器提供的工具。

MCP Server（伺服器）

負責提供工具、資源或提示範本，接收呼叫並執行允許的操作。

例：庫存 MCP 伺服器提供「查詢庫存」工具，背後再向庫存系統取資料。

容易混淆：Client 不等於語言模型；Server 也不等於模型服務。MCP 定義的是工具與資料如何被提供、發現及呼叫。

從連線到查詢：完整操作順序

  1. 在 n8n 建立 AI Agent，選用 Groq 模型。
  2. 加入 MCP Client Tool，設定可信任的 MCP 伺服器位址與授權方式。
  3. 客戶端取得工具清單與輸入規格。
  4. 模型依使用者問題選擇工具，n8n 代為發出呼叫。
  5. 伺服器驗證權限、查詢資料，再回傳結果。
  6. 代理根據工具結果回答，附上資料時間；查詢失敗不得猜測。

適合 MCP 的情況

同一套工具要讓多個 AI 應用共用；希望集中維護工具介面；外部服務已有可信任的 MCP 伺服器。

不一定需要 MCP

只有一個固定 HTTP 查詢、n8n 原生節點已能完成，或任務根本不需要模型自主選工具。

互動案例：庫存查詢 MCP

切換情境，觀察代理應該呼叫什麼工具、如何處理例外。這是教學模擬，不會連到真實伺服器。

企業落地的六項檢查

工具治理

工具是誰提供的？版本變更後，呼叫格式是否相容？

最小權限

讀取與修改資料應分開授權，避免代理拿到過大的權限。

資料可信度

回傳資料是否有來源、時間與必要的欄位驗證？

失敗處理

逾時、限流、斷線時是否重試？重試會不會重複寫入？

提示注入

外部工具回傳的文字不能被當成系統指令。

稽核追蹤

能否記錄誰呼叫哪個工具、參數、結果與核准紀錄？

參考：MCP 官方介紹 · n8n MCP Client Tool

▤03｜Skill：把工作方法寫成可重用的說明

Skill 可以把一項任務的做法、規則、範例與注意事項整理成檔案，供支援技能機制的代理按需使用。這一章重點是「怎麼寫得清楚、能驗證」，而不是背誦格式。

Skill、工具與代理有什麼不同？

Skill：告訴代理怎麼做

例如：報價前先檢查信用、成本、產能；缺資料時一律送人工確認。

Tool：讓代理真的去做

例如：查詢庫存、計算毛利、呼叫系統 API。

Agent：決定下一步做什麼

依任務與現有資訊，選擇是否使用工具、何時完成。

MCP：連接外部工具的方式

讓客戶端發現並呼叫伺服器提供的工具；本身不是工作規則。

重要：Skill 不會自動帶來執行權限，也不等於子代理。不同產品支援 Skill 的方式不完全相同；在 n8n 可以先把技能內容當成可重用的指令或文件，透過工作流程載入。

Skill 的基本寫法：從需求到檔案

  1. 名稱與用途：讓代理知道何時該使用這項技能。
  2. 輸入：列出需要的資料與必要欄位。
  3. 步驟：依順序描述檢查、計算、判斷與輸出。
  4. 限制：哪些資料不可猜測？哪些動作不得執行？
  5. 輸出格式：讓下游流程可以穩定讀取。
  6. 測試：至少包含正常、缺資料、異常及工具失敗。

常見檔案格式為 SKILL.md。檔案前方的中繼資料通常包含名稱與說明；實際欄位及載入方式應依所使用的平台規範調整。

一鍵帶入：三種 Skill 寫作範例

點選案例即可顯示完整範本，再複製或下載成 SKILL.md。學生可直接修改內容進行練習。

▦04｜系統架構圖鑑
A｜固定 Workflow：不需要 Agent 也能做好
排程觸發→SQL 查詢→條件判斷→通知
流程固定且判斷條件可以寫清楚時，優先使用固定流程。
主要好處
  • 成本低：不需要每一步都呼叫模型
  • 容易測試：同樣輸入應得到同樣結果
  • 容易稽核：每個條件和動作都有明確紀錄
缺點與瓶頸
  • 遇到模糊問題時，無法自行理解意圖
  • 規則一多，維護與例外分支會變複雜
  • 上游資料錯誤仍可能造成錯誤通知
適用案例
庫存門檻通知
每天查詢安全庫存，低於門檻即通知採購
MES 與 SAP 對帳
比對固定欄位與數量差異，輸出異常清單
設備點檢提醒
依設備週期建立工單與逾期通知
落地前要確認的問題（點開檢查）
  • 門檻值由誰維護？
  • 查詢失敗是否重試、是否避免重複通知？
  • 資料更新時間是否符合業務需求？
選型提醒：若只需要「查詢數值 → 比對門檻 → 發送通知」，不需要 Agent。
B｜Single Agent + Tools：最常見的基準架構
使用者問題→單一 Agent
模型選工具
↔查詢庫存 Tool成本計算 Tool製令查詢 Tool
需要理解使用者提問，並依問題決定查詢哪個系統時使用。
主要好處
  • 開發快：一個代理即可串接多種工具
  • 對話自然：使用者不必記住查詢欄位
  • 容易建立基準：適合先量測品質與成本
缺點與瓶頸
  • 工具太多時，模型容易選錯或漏用
  • 上下文累積後，延遲與成本可能增加
  • 模型可能把推測當成查詢結果
適用案例
自然語言查庫存
使用者問「A 料還夠生產三天嗎？」代理查庫存與日耗量
製令狀態助理
查詢製令、報工與設備資訊，整理進度
業務報價建議
查信用、成本與產能，產生有依據的建議
落地前要確認的問題（點開檢查）
  • 查詢結果是否包含來源與更新時間？
  • 查詢權限是否限制為唯讀？
  • 缺資料時是否回覆「待確認」而非猜測？
選型提醒：資料查詢、數值計算應做成工具；不是每個工具都要變成 Agent。
C｜Supervisor + Sub-Agents：委派與上下文隔離
Supervisor→信用分析子代理利潤分析子代理交期分析子代理→整合建議
當子任務具有明確輸入輸出，且獨立分析有好處時使用。
主要好處
  • 分工清楚：各子代理只需掌握專業資訊
  • 上下文隔離：避免所有資料塞進主代理
  • 獨立任務可平行處理，縮短部分等待時間
缺點與瓶頸
  • 主代理可能分派錯任務或漏掉任務
  • 子代理回傳摘要可能遺失重要證據
  • 重複查詢、合併結果會增加成本
適用案例
跨領域合約審查
法務、技術與資安分別審查，再由主代理彙整
大型故障診斷
設備、網路、應用系統各自調查證據
報價可行性分析
信用、毛利、交期分別分析，再統一決策
落地前要確認的問題（點開檢查）
  • 每個子代理的輸入、輸出格式是否固定？
  • 主代理如何判斷子代理失敗或結果衝突？
  • 分工後的收益是否高於額外模型呼叫成本？
選型提醒：若只是呼叫三個固定 API，不必建立三個子代理；直接呼叫工具更簡單。
D｜Multi-Agent 協作：有明確協作價值才採用
規劃代理→分析代理→審查代理↺核准閘門
不同角色需要提出意見、互相質疑或修正結果時才採用。
主要好處
  • 多角度審查：能暴露單一分析的盲點
  • 可建立「提出方案 → 審查 → 修正」機制
  • 不同代理可採用不同資料與權限
缺點與瓶頸
  • 代理可能互相附和，並不代表真正驗證
  • 反覆討論容易造成成本與延遲上升
  • 責任歸屬、停止條件與除錯更困難
適用案例
重大設備改善提案
工程代理提出方案，安全代理檢查風險，成本代理估算效益
軟體需求審查
需求、測試、資安角色交叉檢查規格
供應鏈風險評估
採購、交期與財務角色提出相互制衡的判斷
落地前要確認的問題（點開檢查）
  • 代理意見衝突時誰有最終決定權？
  • 是否設定最多迭代次數與逾時？
  • 審查代理是否取得獨立證據，而非重述前一位代理？
選型提醒：多個代理一起回答，不等於品質更高；要用相同測試集證明改善。
E｜Hybrid：企業常用的受控混合式架構
固定流程控制器→Agent 分析→規則驗證→人工核准
涉及交易、設備控制、財務或法遵時，通常值得優先評估。
主要好處
  • 風險可控：重要操作由規則與授權把關
  • 保留彈性：模型處理非結構化資訊
  • 易於稽核：能記錄建議、證據、核准者與執行結果
缺點與瓶頸
  • 流程設計較費工，需定義每個控制點
  • 人工作業可能形成瓶頸
  • 規則與模型結論不一致時需要處理機制
適用案例
生產排程調整
代理提出調整建議，系統驗證產能，再由主管核准
採購申請
代理整理供應商資料，超過金額門檻時送審
設備異常處置
代理分析警報，實際停機指令由授權流程執行
落地前要確認的問題（點開檢查）
  • 哪些操作絕對不能由模型直接執行？
  • 核准前後資料若改變，是否重新驗證？
  • 失敗時能否撤銷、補償或交由人工接手？
選型提醒：讓 Agent 提建議，不代表讓 Agent 直接修改 ERP、MES 或控制設備。
